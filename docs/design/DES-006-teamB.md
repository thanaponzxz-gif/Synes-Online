# DES-006 · ผลทีม B (lane/combo)
**สถานะ:** ส่งตรวจทีม A · ครอบคลุมเฉพาะ §1 combo (กล้อง/HUD/ภาพเป็นสายอื่น) · ไม่ได้ตรวจบนเครื่องจริง: **ยังไม่ตรวจ** FPS/ความรู้สึกบนมือถือ

## §1 combo

### สิ่งที่ทำ (ตรงตามตาราง DES-006 §1)
- 3 ruleset แบบ tick จำนวนเต็ม (30 Hz) ใน `shared/data/tuning.ts` → `COMBO_TICKS`: A 12/12/18 hit 5/5/8 · B 13/13/20 hit 6/6/9 · C 15/15/22 hit 6/6/10 · buffer 8 tick · reset 18 tick นับจากท้ายท่า · ดาเมจ 12/12/22, ระยะ/มุมเดิม (ใช้ `PLAYER.combo[step].dmg/range`) · ไม่ชดเชยดาเมจ/HP · การเดินระหว่างฟัน 35% เดิม · Auto ใช้ค่าเดียวกับผู้เล่น (ผ่าน input ปกติ)
- **ค่าเริ่มต้นคือ `combat-1`** (ค่าเดิมทุกตัว, ทดสอบ golden ต่อ tick ว่าเหมือนเดิมทุกไบต์: 11 เคส สร้างไว้ก่อนแก้โค้ด `tests/fixtures/combat1-golden.json`) · เลือกด้วย `?combo=A|B|C` (ค่าอื่น = combat-1) เหมือน `?dodgecd=`
- `rulesetVersion: 'combat-1'|'combo-A'|'combo-B'|'combo-C'` แยกจาก `inputFormatVersion` (v1/v2) อยู่ใน **run envelope**: client ส่งใน `/api/run/start` พร้อม `tuningHash` (16 hex, `shared/sim/ruleset.ts`), server เก็บใน run record แล้ว replay ด้วย ruleset ที่บันทึกตอน start เสมอ (ตอน finish ส่ง ruleset มาได้แต่ต้องตรงกับที่บันทึก ไม่งั้น `ruleset-mismatch`) · ไม่มี field = `combat-1` · ruleset ที่ไม่รู้จัก → 422 `bad-ruleset` · hash ไม่ตรงกับของ server → 422 `tuning-mismatch` · ไม่ได้ยัดอะไรลงในปุ่ม 8 บิต/tuple
- `World(seed, variant, ruleset)`, `replayRun(seed, log, ms, variant, ruleset)`; renderer ไม่ถูกแตะ (ยังอ่าน `swingT/swingDur` เป็นวินาที ซึ่ง ruleset ใหม่ตั้งให้สอดคล้องกับ tick)

### การตีความที่เลือก (ตามตัวอักษรที่สุด) และคำถามถึงทีม A
1. **หน้าต่างต่อท่า.** โค้ดเดิมต่อท่าถัดไปได้เมื่อท่าเดินไป 62% (ไม่ต้องรอจบท่า). ตาม §1 ("ระยะท่า 12/12/18", รวม 42 tick, hit/s 2.14) ผมตีความว่า ruleset ใหม่ต้อง **รอจบท่าเต็ม `dur` tick ก่อนต่อ** (ไม่มีการตัดที่ 62%). **Q-1:** ถูกต้องไหม หรือต้องการคงหน้าต่างต่อท่าที่ x% ของ dur?
2. **baseline จริงไม่ใช่ 1.14 s.** วัดจาก sim (`npx vite-node tools/qa/combo-cadence.ts`): combat-1 กดรัว 3 ท่าวนครบใน **22 tick = 0.73 s** (ท่า 1→2 6 tick, 2→3 6, 3→1 10 เพราะต่อที่ 62%; hit ที่ 3/3/6 tick หลังเริ่มท่า). ตัวเลข 0.32/0.32/0.50 = 1.14 s เป็นระยะท่าเต็ม ไม่ใช่จังหวะจริง. ผลคือ A (42 tick) ช้ากว่าของเดิม **~1.9 เท่า**, B 2.1 เท่า, C 2.4 เท่า (ไม่ใช่ 1.2–1.5 เท่า) · บอทใช้เวลาสู้บอสเพิ่มจาก ~28 s เป็น 44/48/52 s. **Q-2:** ตั้งใจให้ช้าลงขนาดนี้ไหม หรืออยากให้ ruleset ใหม่ต่อท่าที่ ~62% (A ≈ 7/7/11 tick ต่อท่า)? ผมไม่เปลี่ยนเอง
3. **นับ tick:** tick ที่เริ่มท่า = 0 (เหมือนสกิล, DES-001) → hit เกิดใน tick ที่ `เริ่ม + hit` พอดี; ท่าถัดไปเริ่มได้ใน tick `เริ่ม + dur`. buffer 8 tick นับรวม tick ที่กด (กดก่อนท่าจบ ≤7 tick ยังติด, 8 tick ไม่ติด) · combo reset: ว่าง 17 tick หลังจบท่ายังต่อ, 18 tick รีเซ็ต. **Q-3:** ตรงกับที่ตั้งใจไหม
4. **hash:** `tuningHash` เป็น fingerprint (FNV-1a สองรอบ, ไม่ใช่ลายเซ็น) ครอบ PLAYER/ENEMIES/SKILLS/ULT/CONE_INNER_R/TICK + ค่า combo ของ ruleset. ใช้ตรวจ client/server drift เท่านั้น ไม่กันการโกง (server replay ด้วยค่าตัวเองอยู่แล้ว) **Q-4:** ต้องการ hash ของ `level.ts` ด้วยไหม
5. ชื่อถาวรหลังเลือก (เช่น `combat-2`): ยังไม่ตั้ง; เพิ่มชื่อใน `RULESETS` + `COMBO_TICKS.sets` เมื่อเจ้าของเลือก
