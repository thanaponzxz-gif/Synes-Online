**SEC-4 · P3 · replay ทำงานแบบซิงโครนัสบน event loop ตัวเดียว (วัดได้ 84–125 ms/ครั้งที่ log ยาวสุด)**

### 1.2 เครือข่าย / การโหลด / วงจรชีวิต (ผู้เล่นรู้สึกได้)

**NET-1 · P3 · `net.start` ไม่มี timeout และ `loadKit` ไม่มี timeout: เซิร์ฟเวอร์ที่เชื่อมต่อแล้วไม่ตอบทำให้จอค้าง**

- แนวทางแก้: timeout 3–5 วินาทีแล้วถอยเป็นออฟไลน์/ procedural kit พร้อมข้อความ · เปลี่ยนที่ผู้เล่นเห็น: เล็กน้อย (ข้อความ/ทางสำรอง) → **ต้องให้ทีม A ตัดสินข้อความ UI** · CC · S

## 4. สิ่งที่ยังไม่ทราบ / ตรวจไม่ได้
- ประสิทธิภาพ client ทั้งหมดในหัวข้อ PERF ไม่ได้วัดบนอุปกรณ์จริง (Android / iPhone / PC ยังไม่ได้ทดสอบ) และไม่มีเบราว์เซอร์ headless ที่วัดเวลา frame ได้ใน container นี้ ขนาดผลของ layout thrash / GC churn จึงไม่ทราบ
- ความเข้ากันได้ของ replay ข้ามเอนจิน: ซิมใช้เฉพาะ `+ - * /` และ `Math.sqrt` จึงควรตรงกันบน V8 กับ JavaScriptCore แต่ไม่มีเทสต์ที่รัน log เดียวกันบน iPhone/Safari เทียบกับ Node จึงยืนยันไม่ได้ว่าไม่มี desync จริง
- การกู้ WebGL context (LC-2): ไม่ได้ทดสอบว่าถ้าไม่ `buildLevel` ซ้ำ three จะกู้ภาพได้ครบหรือไม่
- วิธี deploy จริง (reverse proxy? CDN? รันหลาย process?) ไม่ทราบ ซึ่งกำหนดน้ำหนักของ SEC-3, SEC-2, NET-5 (บน GitHub Pages ที่เปิดอยู่ตอนนี้ไม่ใช้ `server/` เลย ผู้เล่นทุกคนอยู่ในโหมดออฟไลน์)
- ไม่ทราบว่ามีโฟลเดอร์พี่น้องใดนอกจาก `dist-spike` อยู่บนเครื่อง production จึงประเมิน SEC-1 ได้เป็น P2 (มีเงื่อนไข) ไม่ใช่ P1
- ไม่ได้ตรวจ CSS/HTML (`src/style.css`, `index.html`) ในแง่ layout/ความสามารถเข้าถึง นอกจากหา sink `innerHTML`
- ไม่ได้ตรวจ `tools/qa/*`, `tools/blender/*`, `spike/*` และเนื้อหาไฟล์ GLB (ถือว่านอกขอบเขต)
- ไม่ได้ตรวจประวัติ git เต็มหา secret (ตรวจเฉพาะ working tree ด้วย `git grep`) repo เป็น Public จึงควรให้สแกนประวัติ (`run_secret_scanning`) เป็นขั้นแยก
- ปัญหาที่ระบุว่ารู้อยู่แล้ว (F1–F3, TD-1/TD-2, KPI-001, P-4, ปุ่มโดนต้นไม้บัง, เวลาโหลด headless, เฟสแอนิเมชันจาก `Object3D.id`) ไม่ได้รายงานซ้ำ
